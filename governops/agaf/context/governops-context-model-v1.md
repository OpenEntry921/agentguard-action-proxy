# GovernOps Context Model v1

## 1. Context Overview

GovernOps does not evaluate a simple isolated action.

GovernOps evaluates the context in which an action occurs.

In GovernOps, a runtime decision is interpreted as the combination of:

```text
Policy
+
Identity
+
Context
↓
AgentGuard
```

Policy defines the control objective, Identity defines the controlled actor, and Context explains the surrounding runtime conditions that make a decision safe, suspicious, or enforceable.

The Context Model v1 is a design document only. It defines the runtime context structure that GovernOps may evaluate in future architecture stages. It does not implement runtime behavior, enforcement logic, or AgentGuard code.

## 2. Context Entity Definition

A Context Entity represents the captured runtime evidence around an agent decision.

| Field | Type | Description |
| --- | --- | --- |
| `context_id` | string | Unique identifier for the captured context instance. |
| `user_request` | string or number | Original user intent or requested action before agent interpretation. |
| `agent_decision` | string or number | Action or decision produced by the agent after processing the request. |
| `prompt_hash` | string | Hash of the prompt context used for the decision. |
| `rag_hash` | string | Hash of retrieved RAG material used during the decision. |
| `reputation_score` | number | Trust or reputation score associated with the actor, agent, or runtime identity. |
| `risk_score` | string or number | Computed risk level or numeric score derived from context evaluation. |
| `temperature` | number | Model sampling temperature used for the decision. |
| `seed` | number or string | Deterministic seed value when available. |
| `embedding_delta` | number | Measured semantic distance between the request, retrieved context, and resulting decision. |
| `timestamp` | string | Time when the context was captured, preferably in ISO 8601 format. |

Example shape:

```yaml
context_id: ctx-2026-0001
user_request: 5000000
agent_decision: 50000000
prompt_hash: sha256:prompt-example
rag_hash: sha256:rag-example
reputation_score: 65
risk_score: HIGH
temperature: 0.2
seed: 42
embedding_delta: 0.37
timestamp: 2026-06-24T00:00:00Z
```

## 3. User Request Definition

The User Request is the original user instruction, intent, or requested transaction before the agent transforms it into a decision.

Example:

```yaml
user_request: 금 500만원 구매
```

This means the user requested a gold purchase worth 5,000,000 KRW. GovernOps treats this as the baseline intent. Later context evaluation compares the agent's decision against this baseline to identify deviation, amplification, or suspicious reinterpretation.

## 4. Agent Decision Definition

The Agent Decision is the decision, action, or execution-ready instruction generated by the agent after processing the user request, prompt context, RAG context, model parameters, and identity state.

Example:

```yaml
agent_decision: 금 5000만원 구매
```

This means the agent produced a gold purchase decision worth 50,000,000 KRW. Because this is materially larger than the original request, GovernOps can evaluate whether the decision should be blocked, reviewed, scored as high risk, or recorded for audit.

## 5. Prompt Context Definition

Prompt Context describes the prompt state that influenced the agent decision.

| Field | Type | Description |
| --- | --- | --- |
| `prompt_hash` | string | Hash of the complete prompt context used for the decision. |
| `system_prompt_hash` | string | Hash of the system prompt or governing instruction layer. |
| `prompt_version` | string | Version identifier for the prompt template or prompt policy package. |

Prompt Context allows GovernOps to determine whether a decision was made under an approved prompt version and whether prompt drift or prompt tampering may have occurred.

## 6. RAG Context Definition

RAG Context describes the retrieval-augmented generation evidence used by the agent.

| Field | Type | Description |
| --- | --- | --- |
| `rag_hash` | string | Hash of the retrieved material set used for the decision. |
| `rag_source_count` | number | Number of retrieved sources considered by the agent. |
| `rag_integrity_score` | number | Integrity score representing source trust, freshness, completeness, or consistency. |

RAG Context helps GovernOps determine whether the agent relied on sufficient and trustworthy retrieval evidence before producing a decision.

## 7. Reputation Context Definition

Reputation Context describes historical trust signals associated with the actor, identity, agent, or runtime environment.

| Field | Type | Description |
| --- | --- | --- |
| `reputation_score` | number | Current reputation score used during context evaluation. |
| `historical_violation_count` | number | Count of prior policy violations associated with the identity or agent. |
| `previous_review_count` | number | Count of previous manual reviews, escalations, or governance interventions. |

Reputation Context gives GovernOps a way to adjust risk based on historical behavior rather than evaluating each decision in isolation.

## 8. Model Context Definition

Model Context describes the model configuration used when the agent decision was generated.

| Field | Type | Description |
| --- | --- | --- |
| `model_name` | string | Name of the model used for the decision. |
| `temperature` | number | Sampling temperature used for generation. |
| `seed` | number or string | Seed value used for deterministic or reproducible execution when available. |
| `model_version` | string | Version identifier of the model or deployment. |

Model Context helps GovernOps reason about reproducibility, volatility, and whether a decision was generated under an approved model configuration.

## 9. Context Risk Evaluation Definition

Context Risk Evaluation defines how GovernOps can identify risky runtime conditions by comparing context fields.

Example rule:

```text
reputation_score < 70
OR
rag_integrity_score < 80
OR
agent_decision > user_request * 5
```

This rule means that a decision may be considered risky if any of the following are true:

- the reputation score is below 70;
- the RAG integrity score is below 80;
- the agent decision is more than five times larger than the original user request.

The purpose is not to enforce policy in this document. The purpose is to define the context signals that a future GovernOps runtime or decision record model may evaluate.

## 10. Financial Example

Example financial context:

```yaml
user_request: 5000000
agent_decision: 50000000
deviation: 900%
risk_score: HIGH
```

In this example, the user requested a 5,000,000 KRW purchase, but the agent decision became a 50,000,000 KRW purchase. The increase from the requested amount to the decision amount is 45,000,000 KRW, which is a 900% deviation from the original request.

Because the decision is ten times the requested amount, GovernOps can classify the context as high risk for review, enforcement, or audit in later architecture stages.

## 11. GovernOps Runtime Connection

Policy defines what should be controlled.

Identity defines who should be controlled.

Context explains why control is required at this moment.

Together, these three layers allow AgentGuard to evaluate not only whether an action is allowed, but also whether the runtime conditions surrounding that action make it risky.

```text
What to control: Policy
Who to control: Identity
Why control now: Context
```

## 12. Context Lifecycle

The GovernOps Context Lifecycle is:

```text
Capture
↓
Evaluate
↓
Score
↓
Enforce
↓
Record
```

- **Capture**: Collect runtime evidence such as request, decision, prompt hash, RAG hash, reputation, and model parameters.
- **Evaluate**: Compare captured fields against context risk criteria.
- **Score**: Produce a risk score or risk level from the evaluated context.
- **Enforce**: Apply a future governance action based on policy, identity, and context.
- **Record**: Persist the decision and context evidence for audit and traceability.

This lifecycle is architectural only in v1. Runtime implementation, policy enforcement, ephemeral tokens, interceptors, engines, and TypeScript code are intentionally out of scope.
